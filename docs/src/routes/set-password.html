概要

オーナーが scripts/invite-user.ts で招待した利用者が、 招待メールのリンクを踏んだ先で初回パスワードを設定するページです。 公開サインアップを無効化しているこのアプリで、新しい利用者が アカウントを使えるようになる唯一の入り口です。

他の認証まわりのページと違い、このページはサーバー関数を 一切呼びません。ブラウザ用 Supabase クライアント （integrations/supabase/client.ts）を直接使います。

コード解説

なぜサーバー関数を経由しないのか。 supabase.auth.admin.inviteUserByEmail()（招待スクリプト scripts/invite-user.ts が呼ぶ API）は PKCE 非対応です。 Supabase 公式ドキュメントいわく、招待する側（オーナー）とリンクを踏む側 （招待された利用者）でブラウザが異なるため、同一ブラウザ内での コード検証を前提とする PKCE の安全性を担保できないからです。そのため 招待リンクの URL には ?code=... ではなく #access_token=...&refresh_token=...&type=invite というハッシュフラグメントが付きます。@supabase/ssr の createBrowserClient はデフォルトで detectSessionInUrl: true になっており、 マウント時にこのハッシュフラグメントを自動的に検出してセッションを 確立します。つまり、このページが読み込まれた時点で、ブラウザ側の クライアントはすでにログイン状態になっています。

これが成立するのは、Supabase 公式ドキュメント（Auth Server-Side Rendering の Advanced guide）が明示するとおり、セッション用 Cookie を あえて httpOnly にしていない（integrations/supabase/server.ts のコード解説を参照）ためです。httpOnly にしてしまうと、ブラウザ側の JavaScript から一切 Cookie を読めなくなり、この自動セッション確立が 機能しなくなります。 

const supabase = getSupabaseBrowserClient()
const { error: updateError } = await supabase.auth.updateUser({ password })
if (updateError) {
  setError(authErrorMessage({ code: updateError.code, message: updateError.message }))
  return
}
await navigate({ to: '/', replace: true })

すでに確立されているセッションに対して、新しいパスワードを設定する だけです。成功すれば通常のログイン済みユーザーとして扱われ、 /（_authed.index.tsx）へ遷移します。 エラーメッセージの変換に login.ts と同じ authErrorMessage を再利用しているため、 weak_password（パスワードが簡単すぎる）のような Supabase 側のバリデーションエラーも自然に日本語で表示されます。
