概要

整備記録を新規作成するサーバー関数です。整備記録の新規登録ページ （_authed.vehicles.$vehicleId.records.new.tsx）から、 「どの車両の記録か（vehicleId）」と「記録の内容 （recordSchema で検証済みの入力）」を受け取って挿入します。

このファイルの見どころは、性質の異なる2つのスキーマ （車両スコープと記録内容）を1つの入力スキーマに合成する方法です。 Phase 5 の vehicles/server/update.ts が使った vehicleIdSchema.extend(vehicleSchema.shape) という手法は ここでは使えません。詳しくは下記のコード解説を参照してください。

コード解説

const createRecordSchema = vehicleScopeSchema.extend({ record: recordSchema })

recordSchema（lib/record-schema.ts）は 「作業内容が『その他』なら自由入力必須」という制約を .refine() で表現しているため、内部的には ZodEffects になっており .shape プロパティを持ちません。そのため vehicleScopeSchema.extend(recordSchema.shape) という Phase 5 と同じ書き方はできません。 代わりに record という1つのフィールドとして丸ごとネストさせています。 ネストしたフィールドの型がどんな Zod スキーマであっても .extend() 自体は成立するため、この制約を回避できます （実装前に node -e で実際に動作を確認済み）。 結果として入力の形は { vehicleId, record: { performedOn, workType, ... } } という2階層になります。 

export async function createRecordHandler(
  input: CreateRecordInput,
  deps: CreateRecordDeps,
): Promise<MaintenanceRecordRow> {
  const { data, error } = await deps.supabase
    .from('maintenance_records')
    .insert({
      vehicle_id: input.vehicleId,
      performed_on: input.record.performedOn,
      work_type: input.record.workType,
      work_type_other: input.record.workTypeOther,
      odometer_km: input.record.odometerKm,
      part_detail: input.record.partDetail,
      note: input.record.note,
    })
    .select()
    .single()
  if (error) {
    throw new Error(error.message)
  }
  return data
}

キャメルケースの入力をDBのスネークケース列名へマッピングして挿入します。 user_id を渡さないのは vehicles/server/create.ts と同じ理由で、 列の既定値 auth.uid() に委ねることでクライアントによる詐称の余地を 無くしています。vehicle_id は入力からそのまま渡しますが、 他人の vehicle_id を指定した場合は複合外部キー (vehicle_id, user_id) がDBレベルで拒否します （RLS だけでは防げない整合性チェックであることが、この制約が存在する理由そのものです）。 

export const createRecordFn = createServerFn({ method: 'POST' })
  .validator(createRecordSchema)
  .handler(({ data }) => createRecordHandler(data, { supabase: createSupabaseServerClient() }))

呼び出し側（ルート）は createRecordFn({ data: { vehicleId, record: input } }) という形で呼びます。vehicleId と記録の内容を明確に分けて渡すことで、 「どの車両の下に作るか」というルーティングの関心事と、 「記録として何を保存するか」というフォームの関心事を呼び出し側でも分離できます。
