概要

整備記録の新規登録・編集で共用するフォームです。 features/vehicles/vehicle-form.tsx（Phase 5）と同じ役割・同じ設計方針 （素の HTML + Zod、送信時に recordSchema.safeParse() で検証してから onSubmit を呼ぶ）を踏襲しています。

Phase 3 で作成済みの3つの純粋関数を UI に接続する点が、このファイルの中心的な役割です: 作業内容が「その他」のときだけ自由入力欄を出す（work-types.ts）、 走行距離が既存記録と矛盾していないか警告する（odometer.ts）、 部品/型式の入力候補を出す（呼び出し側が作った part-suggestions.ts の結果を <datalist> として表示する）。

partSuggestionsList と existingReadings は、 どちらもこのフォーム自身では取得しません（lib/ の純粋関数と同じく Supabase を知らない）。呼び出し側のルートが listPartDetailsFn/listRecordsFn で取得したデータを part-suggestions.ts/そのまま整形して渡します。 編集時、existingReadings には編集対象の記録自身を含めないのが 呼び出し側の責務です（自分自身と比較して「逆行している」と誤検知させないため）。 

function handleWorkTypeChange(next: WorkType) {
  setWorkType(next)
  if (!isOtherWorkType(next)) {

  }
}

作業内容のプリセットに戻したとき、隠れる自由入力欄の値もクリアします。 こうしないと、一度「その他」を選んで文字を入力した後にプリセットへ戻した際、 画面には見えない workTypeOther の値が state に残ってしまい、 次に再び「その他」を選んだときに古い値が復活してユーザーを混乱させます。

function computeRegressionWarning(
  performedOn: string,
  odometerKm: string,
  existingReadings: OdometerReading[],
): boolean {
  if (!isDateString(performedOn) || odometerKm === '') {
    return false
  }
  const parsedOdometerKm = Number(odometerKm)
  if (Number.isNaN(parsedOdometerKm)) {
    return false
  }
  return isOdometerRegression(
    { performedOn: performedOn as DateString, odometerKm: parsedOdometerKm },
    existingReadings,
  )
}

まだ検証を通していない入力途中の文字列（performedOn/odometerKm は state 上ただの string）を、isDateString で実在する日付か 確認してから lib/odometer.ts の isOdometerRegression に渡します。 日付が未入力・不正、または走行距離が未入力・数値でない間は警告を出さない （false を返す）ことで、入力途中に誤った警告が点滅するのを防いでいます。 

{regressionWarning && <p role="status">走行距離が他の記録と前後関係が逆になっています。ご確認ください。</p>}

{error && <p role="alert">{error}</p>}

走行距離の逆行警告は role="status"、入力検証エラーは role="alert" と役割を分けています。前者は「送信をブロックしない 参考情報」（走行距離計を交換した等、正当な理由で矛盾するケースがありうる）、 後者は「送信できない致命的な問題」だからです。テスト上もこの2つを別の ロールとして区別して検証できます。

ブラウザ標準の <datalist> でサジェストを実現しています。 専用のコンボボックスUIコンポーネントを作らず標準機能に任せることで、 キーボード操作・スクリーンリーダー対応をブラウザに委ねられます。 テキストとしても選択肢を出すため <option> に value と子テキストの両方を設定しています。
