概要

ログイン画面のフォーム入力（メールアドレス・パスワード）を検証する Zod スキーマです。このアプリは公開サインアップが無いため「新規登録の バリデーション」は存在せず、ここで扱うのは既存アカウントでの ログイン入力のみです。

サーバー関数（ログイン処理の入口）とクライアント側のフォームの両方で このスキーマを共有し、「クライアント側の検証を信用しない」という プロジェクト規約（CLAUDE.md）どおり、実際の認証 API を 呼ぶ前に必ずこの検証を通す想定です。

構成

名前種別説明
loginSchemaconst（export）ログインフォームの Zod スキーマ

コード解説

export const loginSchema = z.object({
  email: z
    .string()
    .trim()
    .min(1, 'メールアドレスを入力してください')
    .email({ error: 'メールアドレスの形式が正しくありません' }),
  password: z.string().min(1, 'パスワードを入力してください'),
})

export type LoginInput = z.infer<typeof loginSchema>

email — .trim() を先に置いているのが ポイントです。Zod のチェーンは書いた順に適用されるため、 .trim() を .email() より前に置くことで、 前後に空白が入った入力（コピペでありがちな "  user@example.com  " など）でも トリム後の値でメール形式を判定できます。逆の順序だと、空白を含んだ 状態でメール形式チェックが先に走り、正しいアドレスなのに弾かれて しまいます。

.min(1, ...) を .email(...) より前に 置いているのは、未入力時に「メールアドレスの形式が正しくありません」 ではなく「メールアドレスを入力してください」という、より的確な メッセージを最初のエラーとして出すためです（Zod はチェーンした検証をすべて評価して issues 配列に積むため、 画面側は基本的に先頭の issue を表示すればよい設計にしています）。

password — ここでは「空でないこと」だけを検証します。 パスワードの強度要件（大文字・記号を含む、など）はアカウント作成時 （オーナーによる招待後の /set-password 画面）の責務であり、 ログイン画面では「今まさに使っているパスワードが弱いかどうか」を 判定する意味が無いため、ここでは課しません。同じ理由で .trim() も付けていません。パスワードの前後に意図した 空白が含まれるケースを尊重し、黙って値を変えないためです。
