E2E（Playwright）テスト基盤 — Phase 8: 検証とデプロイ

playwright.config.ts ／ e2e/**

概要

実装プランで指定された「Playwright MCP、mobile（iPhone 13 / Pixel 5）と desktop（1280×800）の2プロジェクト」を実現する、ブラウザ越しの エンドツーエンドテスト一式。単体テスト（Vitest）やRLS統合テストとは異なり、 実際に動いている開発サーバーを、実際のブラウザで、実際の開発用Supabase プロジェクトに対して操作する、最も本番に近いレイヤーの検証。

優先順位付きの8シナリオ（ログイン・ルートガード・車検アラート・車検完了・ データ分離・250ccバイク・整備記録・モバイル人間工学）をすべて実装し、 mobile/desktop 両プロジェクトで実行して全件成功させた。

npm run test:coverage（Vitest）とは完全に独立しており、 npm run test:e2e（playwright test）で明示的に実行する。

1. playwright.config.ts — 2プロジェクトと開発サーバーの自動起動

const PORT = 3101
...
projects: [
  { name: 'desktop', use: { ...devices['Desktop Chrome'], viewport: { width: 1280, height: 800 } } },
  { name: 'mobile', use: { ...devices['Pixel 5'] } },
],
webServer: {
  command: `npx vite dev --port ${PORT}`,
  url: BASE_URL,
  reuseExistingServer: !process.env.CI,
  timeout: 120_000,
},

ポート3000は別セッションのnpm run devが使用中の可能性があるため、 Phase 7でポート競合対策として追加した.claude/launch.jsonの vehicle-maintenance-dev-altと同じ考え方でポート3101を使う。 package.jsonのdevスクリプト自体は招待メールの リダイレクトURL設定と結びついているため変更していない。

webServerによりPlaywrightがテスト実行前に自動でdevサーバーを 起動し、テスト終了後に自動で止める。手動で別ターミナルを開いておく必要がない。 

workers: 2,
retries: process.env.CI ? 1 : 2,

実際に動かして初めて分かった調整。ワーカー数を上げすぎると 単一の開発用SupabaseプロジェクトのAuthレート制限（ユーザー作成・サインイン）に 短時間で達し、"Request rate limit reached" が実際に発生した。ワーカー数を2に絞り、 さらにsupabase-admin.ts側にもリトライを実装することで安定させている。

retries: 2も同様に、単一devサーバー・単一Supabaseプロジェクトへの 並行アクセスに起因する低確率のタイミング依存の失敗（実際に確認済み）を 吸収するための調整。

3. supabase-admin.ts — 使い捨てユーザーとロールバック

export async function createTestUser(admin, label) {
  const { data, error } = await withRateLimitRetry(() =>
    admin.auth.admin.createUser({ email, password, email_confirm: true }),
  )
  ...
  const { error: signInError } = await withRateLimitRetry(() =>
    client.auth.signInWithPassword({ email, password }),
  )
  if (signInError) {
    // 作成済みユーザーを削除してから例外を投げる（ロールバック）
    await admin.auth.admin.deleteUser(data.user.id).catch(() => {})
    throw new Error(...)
  }
  return { id: data.user.id, email, password, client }
}

この実装に至る過程で、実際に12件のゴミユーザーが開発用 Supabaseプロジェクトに残留する事故が起きた。初期実装では ユーザー作成が成功した後にサインインが失敗すると（レート制限の 一時的なエラー等）、作成済みユーザーが削除されずに残り続けていた。 原因を特定し、サインイン失敗時に作成済みユーザーを即座に削除する ロールバック処理を追加したうえで、残留していた12件を手動で削除して 解消した。「使い捨てリソースは失敗時も必ず後始末する」という このプロジェクト全体の運用方針を、コードでも保証する形にしている。

withRateLimitRetryは指数バックオフ（1秒→2秒→4秒→8秒）で 最大4回まで再試行する。レート制限以外のエラーや最終試行では 即座に結果を返し、無限にリトライしない。

4. navigation.ts — ハイドレーション待ちで解決した"謎の失敗"

export async function gotoReady(page: Page, path: string): Promise<void> {
  await page.goto(path, { waitUntil: 'networkidle' })
}

調査に時間を要したバグの原因と対策。 page.goto()直後にフォーム操作を行うと、TanStack Startの 開発サーバー（未バンドルのESMを1ファイルずつ読み込む）では Reactのハイドレーションが完了する前にクリックが届くことがあった。 その場合onSubmitハンドラが未アタッチのままブラウザの 素のフォーム送信が発生し、ログイン処理が実行されずに同じ画面へ 戻ってしまう。waitUntil: 'networkidle'を挟むことで、 モジュール読み込みが落ち着いてから操作を始めるようにして解決した。 一時は「TanStack Startのフレームワーク側の問題では」と疑われたが、 後述のgetByLabelの問題とあわせて、最終的にテスト側の タイミング制御の問題だったと判明した。
